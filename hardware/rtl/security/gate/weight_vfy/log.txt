- when storying memory I want a region that can be locked/protected 
- we will first send all the weights from the host computer to the chip
- the computer will then request to lock/protect the values in the address region specified by the instruction (this will be the region of the weights)
    - during this command the chip will run the security layer by hashing the address region and comparing it to a hardcoded value
    - the address region will only be locked when the hash matches 
    - when lock is enabled any write to the weight region is blocked
- security FSM: IDLE, LOAD, FINALIZE, VERIFY, LOCK, EXECUTE, ERROR
    - IDLE: wait for host, memory is unrestricted 
    - LOAD: streaming weights into memory and SHA256 core and actively calculating hash
    - FINALIZE: stop accepting weights, and send finalize flag the sha256 wrapper
    - VERIFY: compare hash vs expected hash 
    - LOCK: freeze weights and lock down system
    - EXECUTE: allows access to normal accelerator functions, with read only access to protected regions
    - ERROR: hash mismatch

- "secure GPU like accelerator with hardware-enforced memory protection, where model weights reside in a region that is cryptographically verified and locked prior to execution"

- current threat model:
    - attacker can: 
        - control instruction stream
        - non-protected memory region
        - input to accelerator
        - can observe output
    - attacker can't:
        - modify weight region after lock
        - modify golden hash /ROT
        - bypass hardware memory protection logic 
- current security goal: “Ensure that only an authenticated set of weights is used during execution, and that those weights cannot be modified after verification.”

- other potential threats that we will not address yet:
    - an attacker reusing valid weights in an unintended way to compute something else
        - a feature we can add is hashing weights and hashing instruction stream and locking both to gurantee that only a specific program can execute 
        - this could be difficult to conduct because if the weight address locations are different it may change the instructions 
    - an attacker could load a second set of weights after verifying a valid set of weights, and perform computations using the second set of weights
        - potential solution: create explicit memory regions for weights and data, and when performing inference commands (MAC) make sure that one of the operands is from the weight memory region

- SHA256 will be implemented using secworks SHA-256 corrputed
    - iterative architecture allows for LUT conservation and also will help performance with our streaming design 

- potential feature we could add is a fault/error state
    - this will disable execution until reset 

- we will need to add a layer on top of the current memory architecture that allows enforcement of write/read OR create a separate memory bank
    - i think that creating a top layer will be effective because we can minimize the interface changes
    - one concern is how we will differenciate between weights, instructions, and input data, but we can just make it standard that weights will always be sent first
    - so the stream of writes to memory will be hashed as it comes in until we are in the FINALIZE_HASH state
    - afterwards we will be in the EXECUTE state, and in this state we will be writing the instructions and/or input data 
    - honestly we could prob ignore the instruction writes because it will most likely be in a separate memory area 
    - in this upper layer we will need to have the ability to lock writes among a set of adddresses
    - the writes into addresses where it is locked will be blocked, this will probably require changes with the communication_controller module to be able to handle write blocks 

- when the hash verification fails, should we go into an error state, or just go back to loading? 
    - we will go directly into an error state, that needs to be restart to activate the accelerator.
    - another design choice, is do we restart the entire chip or just clear the memory. 
    - we will only restart the security module
        - clear the security FSM, restart hash engine
        - note: this leaves a risk of residual data exposure, so it would be beneficial to add secure zeroization, however I don't think we have enough resources to apply this
            - another cheaper solution is to add a read disable feature after failure, but honestly not too useful 

- another concern, overwrites. 
    - With our current design decision during transmission we will be recieving a CRC value and comapre it with our CRC value, if it doesn't match the chip sends a NACK to the host 
    - when the NACK is recieved by the host it retransmits the entire data block to overwrite, if this retransmition occurs during the loading of weights, it will disrupt the hash calculation
    - the design trade off would be creating logic that allows us to handle this issue, or to use an architecture where weights must be streamed continuously, and if an error is discovered restart the security gate and retransmit all the weights
    - honestly I think that this case is rare enough that we wouldn't have to worry about it being a real issue. 
    - will be neccesary to adjust software so that weights are fully retransmit when a NACK is recieved

Main security gate design 
- security FSM: IDLE, LOAD, FINALIZE, VERIFY, LOCK, EXECUTE, ERROR
    - IDLE: wait for host, memory is unrestricted 
    - LOAD: streaming weights into memory and SHA256 core and actively calculating hash
    - FINALIZE: stop accepting weights, and send finalize flag the sha256 wrapper
    - VERIFY: compare hash vs expected hash 
    - LOCK: apply security policy 
    - EXECUTE: allows access to normal accelerator functions, with read only access to protected regions
    - ERROR: hash mismatch, or other error
- when a write command is recieved from the communication_controller, during the LOAD state, it will route the data from the communication_controller to the secure memory wrapper and the SHA256 wrapper
- it will need to keep track of the memory region that needs to be locked
    - to avoid extra logic, it might be good to standarize the weight input with software 
    - we could add logic that keeps track of the region that was loaded, but to save LUTs standarize the following for loading weights:
        - weights will always be sent first
        - the address of the weights will start from 0x0000
        - the weights need to be sent sequentially and in order
        - therefore, the position of each weight is locked, and each weight must be in it's appropriate position for it to pass the security check
        - when a NACK is discovered, the gate will go into ERROR mode (only when loading weights)
            - when this happens the security gate will need to be explicitly reset 
            - the transfer of weights will need to be fully reset 
        - the HW will be making the assumption that the last accessed address is where the weights end 
    - with this design implementation on the SW we can minimize the logic the HW
    - although this is heavily reliant on SW compatibility, even if an attacker has full access to the SW the chip should still be secure with zero trust logic
    - the protected region will be something like this: [0x0000, last_weight_address]
    - important to note that the last_weight_address only gets updated during load
- the hash values that will be compared to will be hardcoded into the chip, but there can be multiple stored hashes
    - when the verify command is called, it will attach a 4 bit sequence that determines which hash value to comapre to
- when a write is blocked because it attempted to overwrite a locked region, it should send a signal to the communication_controller (mem_write_fail)   
    - when the write region is unlocked, then it should send the mem_write_done signal
- during LOAD, if CRC fail, SHA error, transition into the ERROR state 
- when in EXECUTE or ERROR states, the only way to exit is via a security reset signal
- verified and security_fault registers will be needed to contain information about the chip's status
- !== Potential future feature ==!
    - when calculating the hash, we will compute it with a salted value (the address), so the hash input becomes something like HASH({address, address} || data) 
        - this will gurantee that weights are placed in the correct placed
        - this feature will not be implemented in the first round of implementation, because debugging will become more difficult, but should be an easy feature to add in the future
    - the read from the protected region is only from the accelerator, host's request to read from the protected region will be declined. 
        - when the read is attempted, return 0xDEADDEADDEADDEAD
        - this again can be added later, because it will make debugging more difficult, for now host can read from protected region 
    - add security codes to the NACK that is sent 
        - ie we can populate the address region of the header with codes that indicate what kind of error (hash mismatch, CRC fail, write attempt to lock region, SHA failure)
    - another issue with the current design is that an attacker can still use scratch memory to perform computation, after sending a valid model
        - one solution to fix this is to make it so that certain operation must take in one of the inputs from a protected region
        - but how do I differenciate operations that require input from a protected region vs operations that don't require operations from a protected region 
        - this would also require rewritting a good chunk of the implemntation of the operations so that it forces the use of protected regions
        - potential solution: adding meta data to memory, but this would blow up the complexity

- 5/11
    - This current security framework only works with the assumption that this GPU will be used for AI inference, and we will continue building on this security architecture
    - in parallel we will start building a security framework for a GPU that supports AI training as well
    - In the current implementation there are a couple things that we want to implement:
        - make it so that the host can't read from the protected region, when the system is locked
            - when the host attempts to read from the protected region, it will return 0xDEADDEADDEADDEAD when in LOCK, EXECUTE, ERROR states
            - host can read from memory unrestricted when in IDLE and LOAD states
        - support memory access for the chip
            - when the chip accesses protected memory (in execute state), it can read from the region, but it can't write to the region
            - read/write is fully accessibly to scratch memory region
        - when in ERROR state, execution is disabled, protected region is inaccessible by anyone, writes blocked, only resets are allowed
        - therefore, all memory requests in this system must go through the security gate
        - to support the different memory access, we will create a very basic bus controller module
            - this is honestly not neccesary, we're just doing this to help scalability 
            - design specs:
                - it will take in 2 memory bus interface and 2 set of memory status flags
                - the output is 1 memory bus interface, 1 memory status flag set, and the id of where the memory request origniated from
                - this will be connected to the security gate as it's input, so it will need to support these changes
                - for each device, it will also take in a wire that goes up when a request is sent to memory
                - the key feature is the use of memory_request_id
                    - this will likely be the only register in this module
                    - we will define it as REQ_HOST, REQ_CORE, REQ_SEC, REQ_DEBUG
                    - in reality, we will only use REQ_HOST and REQ_CORE, but this is for future scalability
                - the security gate will use the memory_request_id to enforce the different policies for each request
                - this will be a very light weight module consisting of mux 
        - there was a mistake in the implementation where the security gate didn't do the proper handshake with the communication_controller, this was fixed
    - an issue with the current implementation is that the host can take over the bus while the core is waiting for a response
        - we should probably make it so that the bus access can only change when memory status consumed, memory write fail, and memory write done are all 0 
        - or another way to gurantee that transmission is complete

- 5/13
    - we are very limited on the number of LUTs that are available
    - the largest LUT eater in the current system is the SHA256 core
    - our current goal is to reduce the area by removing parallelization
    - some changes to help reduce LUT in SHA256 core
        - removed support for SHA224 (little change)
        - weight strean block index switched to basic case statements, instead of arithmetic based indexing (-4000 cells)
        - removed memory round-index output mux (-400 cells)
        - cycle count increases by about 10X, but this shouldn't be an issue considering we are already bottlenecked by the UART transmission
        - reduced total cells from 10507 -> 6204 (41% reduction)
    - for verification, I'm thinking of using Yosys:
        - https://yosyshq.readthedocs.io/projects/yosys/en/0.46/getting_started/installation.html#targeted-architectures
        - evaluate_sha256_size.sh script to help determine the number of LUTs used
    - additional changes:
        - sha256 wrapper -> -1000 cells
            - removed submit_block_reg which held the final input block into the sha256, instead we submit the block directly without a middle man
        - sha256 core -> -280 cells
            - reduced number of adders in design when updating the digest
            - instead of 8 parallel adds getting processed in 1 cycle, they share 1 adder across 8 cycles
            - this is done by using a MUX
