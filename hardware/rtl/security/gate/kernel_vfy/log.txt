Kernel Verification Design (kernel_vfy):
- security goal: only authenticated kernels may execute, and verified kernels can't be modified while executing
    - protected assets: kernel / instruction memory
    - trusted hardware: security FSM, SHA256 core, golden hash BRAM
    - Untrusted components: host software, uploaded kernel data, input data, data memory, program write requests, launch requests
    - Security gurantees: accelerator core can only execute a kernel if:
        - kernel was streamed into instruction memory
        - streamed bytes were hashed
        - hash matched trusted golden hash
        - instruction memory was locked
        - launch was gated by kernel_verified == 1
- We will use the same core concepts from the security gate design where we use the SHA256 core for hashing
- security FSM: IDLE, LOAD, FINALIZE, VERIFY, LOCK, EXECUTE, ERROR
    IDLE
    No verified kernel is active.
    Host may begin kernel upload with COM_CMD_WRITE_PROGRAM.
    Host can still write/read data memory

    LOAD
    Host is streaming kernel words via COM_CMD_WRITE_PROGRAM
    Each accepted program word is:
        1. written to instruction memory
        2. fed into SHA-256 stream

    FINALIZE
    Host indicates kernel upload is complete via COM_CMD_VALIDATE
    SHA-256 wrapper pads/finalizes message.

    VERIFY
    Security FSM compares computed hash against selected golden hash.
    Golden hash is selected via address field of COM_CMD_VALIDATE

    LOCK
    Program memory writes are disabled.
    kernel_verified is set.

    EXECUTE
    Launch is allowed.
    Core may fetch from locked instruction memory.
    Host may write/read data memory.
    Host may upload a new kernel only when core_busy == 0.

    ERROR
    Security fault state.
    Launch disabled.
    Program writes disabled or ignored except security reset.
    Host must send SECURITY_RESET.

- in this architecture we need to support switching out multiple kernels
    - multiple kernels can be used by a process
- during EXECUTE, if the core isn't busy and a COM_CMD_WRITE_PROGRAM is recieved, we will go into the LOAD state
    - note: the initial COM_CMD_WRITE_PROGRAM contains words so that needs to be written and hashed as well
    - if the core is busy, the write will be rejected and a NACK will be sent back
    - when making the transition, kernel_verified = 0; program_locked = 0; and sha256_reset needs to be pulsed
- when in error state, host will need to send the security reset command 
- a hash failues (VERIFY), sha256 failure (LOAD), crc failure (LOAD), will all cause the state to change to ERROR 
- there will be 40+ hashes stored on the chip
    - these will be declared in a dedicated BRAM chunk
    - these will be managed via a separate module, where the input is the hash number/index and the output is the 256 bit golden hash
    - note: the current validate_model_id is only 4 bits wide, should increase it to at least 6 bits
        - we'll also rename it to validate_kernel_id

- 5/23
    - potential vulnerabilities with the hardware:
        1. CRC failure still writes into instruction memory and goes into the hash stream
            - 2 ways to address this: stall the write/hash till CRC is confirmed or go into the error state after the CRC fails
        2. SHA256 core may not be ready for the next set of data when the cc_prog_we is active. This could lead to instructions that slip into the instruction memory without it being hashed, and/or a word can be skipped causing it to fail the verification (which is fine for the zero trust system)
            - 2 ways to address this as well: either add buffering and backpressure support or go into error state 
        3. when running simulation, kernel_golden_hashes.mem does not get loaded correctly. I don't know if this is because of iverilog or a general issue, will have to come back to this
        4. COM_CMD_VALIDATE that is sent outisde S_LOAD and S_ERROR can deadlock the system
            - in invalid states return validate_fail if validate gets called
            - we could make the system go into error state, but the validate cmd doesn't create vulnerabilities, so I think it is find to just send a NACK
        5. a launch command before validation gets blocked, but the system returns an ACK, making the host think that it launched successfully
            - need to make it so that a NACK is sent when launch is blocked
    - For CRC failure and SHA256 core not being ready, the easy solution is to make them go into error state
        - from actually testing the system, CRC failure is very uncommon, so building an entire response system is likely not good ROI
        - it is unlikely that the SHA256 core is not ready, this is because the delay between each word is significant, due to the UART data transmission constraint 
        - therefore, because both scenarios are unlikely, it would be a good idea to just have our system go into error state, this is me choosing where I should spend my time, but this is a perfectly valid solution, because it doesn't make the security any weaker, it still enforces zero-trust
