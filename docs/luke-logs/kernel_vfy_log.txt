Kernel Verification Design (kernel_vfy):
- security goal: only authenticated kernels may execute, and verified kernels can't be modified while executing
    - protected assets: kernel / instruction memory
    - trusted hardware: security FSM, SHA256 core, golden hash BRAM
    - Untrusted components: host software, uploaded kernel data, input data, data memory, program write requests, launch requests
    - Security gurantees: accelerator core can only execute a kernel if:
        - kernel was streamed into instruction memory
        - streamed bytes were hashed
        - hash matched trusted golden hash
        - instruction memory was locked
        - launch was gated by kernel_verified == 1
- We will use the same core concepts from the security gate design where we use the SHA256 core for hashing
- security FSM: IDLE, LOAD, FINALIZE, VERIFY, LOCK, EXECUTE, ERROR
    IDLE
    No verified kernel is active.
    Host may begin kernel upload with COM_CMD_WRITE_PROGRAM.
    Host can still write/read data memory

    LOAD
    Host is streaming kernel words via COM_CMD_WRITE_PROGRAM
    Each accepted program word is:
        1. written to instruction memory
        2. fed into SHA-256 stream

    FINALIZE
    Host indicates kernel upload is complete via COM_CMD_VALIDATE
    SHA-256 wrapper pads/finalizes message.

    VERIFY
    Security FSM compares computed hash against selected golden hash.
    Golden hash is selected via address field of COM_CMD_VALIDATE

    LOCK
    Program memory writes are disabled.
    kernel_verified is set.

    EXECUTE
    Launch is allowed.
    Core may fetch from locked instruction memory.
    Host may write/read data memory.
    Host may upload a new kernel only when core_busy == 0.

    ERROR
    Security fault state.
    Launch disabled.
    Program writes disabled or ignored except security reset.
    Host must send SECURITY_RESET.

- in this architecture we need to support switching out multiple kernels
    - multiple kernels can be used by a process
- during EXECUTE, if the core isn't busy and a COM_CMD_WRITE_PROGRAM is recieved, we will go into the LOAD state
    - note: the initial COM_CMD_WRITE_PROGRAM contains words so that needs to be written and hashed as well
    - if the core is busy, the write will be rejected and a NACK will be sent back
    - when making the transition, kernel_verified = 0; program_locked = 0; and sha256_reset needs to be pulsed
- when in error state, host will need to send the security reset command 
- a hash failues (VERIFY), sha256 failure (LOAD), crc failure (LOAD), will all cause the state to change to ERROR 
- there will be 40+ hashes stored on the chip
    - these will be declared in a dedicated BRAM chunk
    - these will be managed via a separate module, where the input is the hash number/index and the output is the 256 bit golden hash
    - note: the current validate_model_id is only 4 bits wide, should increase it to at least 6 bits
        - we'll also rename it to validate_kernel_id

    - if a user uploades relu, validates, relu, uploads sigmoid, validate sigmoid, and launch cached relu, board is in validated state, but the state is in reference to the sigmoid
    - a potential attack vector is that a user uploads a corrupted relu, then sends a correct sigmoid, get's sigmoid validated, and run corrupted relu, but this is attack is protected against because the second relu get's attempted to be verified the board will be in an error state
    - however there are 2 other attacks that can be used:
        - right now, we don't have zeroization when a security reset occurs; therefore an attacker can uploaded corrupted kernel, fail validation, security reset, upload good kernel in different address, validate, but launch from the corrupted kernel's address
        - another vulnerability is that an attacker can overwrite the instruction memory in a way that puzzles together there own kernel: an attack uploads/validates kernel at 0x0000; then uploads/validates kernel at 0x0002, overwriting most of the previous kernel; repeat this many times to create a malicious instruction stream, then launch at address 0x0000

        - this significantly improves security, but performance takes a huge hit, because we can't cache kernels, and kernel uploads take a long time

- 5/25
    - !== Security Issue 1 ==#
        - Issue: Residual instruction memory after security reset
            - A security reset originally cleared verification state but did not clear instruction memory. This could allow stale or corrupted instructions to remain resident after fault recovery
        - Attack: an attacker can upload corrupter kernel, do a security reset, upload good kernel, validate, launch from corrupted kernel's address
        - Solution: 
            - 1.1: Add zeroization on reset/security reset
                - pros: fixes the no-zeroization attack vector, easy to implementation, and not too much new logic
                - cons: slight overhead during reset/security reset, but shouldn't be a huge issue
            - 1.2: Address othe security vulnerabilities that allow attackers to exploit the zeroization vulnerability (invalid launch)
                - pros: patches multiple vulnerabilities with one fixes
                - cons: there could be ways to exploit the zeroization vulnerability that I haven't discovered yet 
    - !== Security Issue 2 ==#
        - Issue: we don't enforce validated regions
        - Attack: an attacker uploads/validates kernel at 0x0000; then uploads/validates kernel at 0x0002, overwriting most of the previous kernel; repeat this many times to create a malicious instruction stream, then launch at address 0x0000
        - Solution:
            - 2.1: Program writes must start at address 0x0000 and we will salt the hash with the write address
                - pros: very tight security and can be easily implemented on the hardware
                - cons: performance will take a huge hit, because this effectively removes the caching ability, and only 1 kernel can be stored on the board
            - 2.2: Hash/verify when a new kernel is launched. We will read the kernel instructions from the instruction memory and verify that the kernel is still valid when launching new kernel
                - pros: allows us to continue storing multiple kernels in the insutrction memory
                - cons: the overhead to launch a new kernel is significant, because we will need to read all the instructions for the kernel from instruction memory, and some of them are really huge
                    - this will likely also introduce a lot of new logic 
            - 2.3: Track metadata for validation regions. Track which regions are validated, only the first address in the region is launchable, if any write occurs inside the region then region becomes invalidated
                - pros: allows multiple kernels to live in the cache, significantly less overhead compared to other solutions
                - cons: a lot of new and complex logic but also a completely new design document with brand new modules and concepts 
            - 2.4: Instruction memory blocks. Very similar to 2.3, but instead of dynamic regions we have set block of data (ie 512 bytes)
                - pros: same pros as 2.3, it will likely be easier to manage because there is a set number of blocks, we could also add the salted hash feature if we write_constants
                - cons: same cons as 2.3
            - all these solution address the issue of invalid launch address, overwriting of kernel, these solutions also help to protect against the no zeroization vulnerability
    - for future work, the first thing we should do is implement solution 1.1, assuming we have enough resources
        - to handle security flaw 2, the only option that is viable to keep performance is 2.3 or 2.4, but we don't have enough resources on the Basys 3 FPGA to implement it
