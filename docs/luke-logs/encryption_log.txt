Security goals:
- Host authentication
    - only trusted host can communicate with accelerator (predetermined key)
- device authentication
    - allow for mutual authentication, with each sharing a hardcoded key
- Confidentiality
    - an attacker can't observe model weights or training data in transmission
- integrity
    - modifications to packets are detected before processing
- Replay protection
    - old packets from different sessions can't be used for replay attacks
- Each session uses a fresh set of encyption keys
- Hardware enforced trust
    - authentication, key derivative, packet verification, are all enforced in hardware-controlled security FSM

Threat model:
- attacker can:
    - has full control over communication channel (ie intercept, modify, inject, observe)
    - send commands to accelerator
    - has knowledge of entire protocol structure
- attacker can't:
    - extract keys from the hardware, ie doesn't have physical access to the hardware 

- lightweight IPs that are usable:
    - secworks AES IP
    - secworks SHA256 IP
    - secworks CHACHA IP
    - secworks ROSC_ENTROPY IP
- using all the IPs will take up ~11k LUTs
- we can use these as building blocks for our system
- an ECDH key exchange would be nice, but we don't have the resources both in terms of open-source IP and LUT count
- instead of a ECDH key exchange we can do a hardware-rooted session key derivative
- hardware session key derivative
    - both the FPGA and host will have a predetermined root key (in reality this would likely be transfered using asymetric keys or ECDH)
        - our security assumption is that an attacker has no way of knowing this key
    - the FPGA and host each generate a personal nonce
    - host sends nonce_host to FPGA, and FPGA send nonce_fpga to host
    - when each party recieves the other party's key they will compute a new session key with the following formula: 
        - session_key = SHA256({root_key, nonce_host, nonce_fpga})
    - benefits:
        - each session key is unique 
        - easy to implement, can just build off of the current SHA256 implementation
        - because the root_key and/or its children aren't transfered through the transmission line, it will make it difficult for an attacker to obtain hints on what the root_key may be
        - a matching root_key is used for symmetric authentication
- for generating the nonce_fpga, we will use the CHACHA algorithm as a CSPRNG (cryptographically secure pseudorandom number generator)
    - will use a SHA256 to generate the key for the CHACHA algorithm (entropy conditioning), but this requires a strong entropy source
        - entropy source: ring oscillator jitter (ROSC IP)
    - entire flow for nonce generation: ROSC_ENTROPY -> SHA256 -> ChaCha CSPRNG
    - risks: synthesis optimizations may break the ring oscillator, we may have to do some stuff when trying to synthesize to prevent over optimization
- with the shared key, all payload will be encrypted using AES-CTR (stream cypher)
    - AES-CTR is not really a stream cipher, it is a block cipher operating in stream mode
- because we are using stream cypher, we need an integrity checker
- to gurantee integrity, we will also use a MAC (message authentication code)
    - never mind because apparently this isn't the most secure way of doing things
        - MAC = SHA256({session_key, packet})
            - the MAC will be computed from the RX and sent to the TX, and the MAC will be recomputed at the TX and it will check to see that the recieved MAC is the same a the calculated MAC
    - a more secure method is using HMAC-SHA256
        - 2 keys are used 
        - basic formula: HMAC = SHA256({hmac_key_2, SHA256({hmac_key_1, ciphertext})})
        - the 2 keys are derived from the root hmac key, and doing an XOR with a predetermined constant
            - constants: inner pad (ipad) = 0x36; outter pad (opad) = 0x5c
    - when the HMAC is calcualted by the TX it will be sent to the RX, and the RX will recalculate the HMAC and comapre the 2 HMAC values to verify integrity
- overall the system will have 4 keys:
    - root_key (hard-coded key that both FPGA and HOST have)
    - session_key = SHA256({root_key, nonce_host, nonce_fpga})
    - encryption_key = SHA256({session_key, encryption_constant})
    - hmac_key = SHA256({session_key, hmac_constant})
        - hmac_key will be used to derive the following inside the HMAC:
            - hmac_key_1 = hmac_key ^ ipad
            - hmac_key_2 = hmac_key ^ opad
- the encryption constant, hmac constant, ipad, and opad values are open to the public

Encryption Controller module design
- every encrypted packet has a packet_counter
- RX decryption only occurs after the HMAC is verified
- only the payload will be encrypted, but the entire header (except the SOF) will be fed into the HMAC to ensure nothing was modified
- will add another piece to the header, but this will only be used by the security module 
    - packet_number: these values will be tracked by FPGA and host separately and do not need be synced, it is just there to avoid replay attacks
        - this packet number will be fed into the HMAC generator and the AES encrypter
        - this number is only kept tracked and incremented by the TX
        - RX will not be expecting a particular number, it will just recieve any value and use it for it's decryption and HMAC verification
- new packet format:
    SOF             1 byte   0xAA
    cmd             1 byte
    addr            2 bytes
    len             2 bytes
    packet_counter  2 bytes
    ciphertext      len bytes
    hmac_tag        16 bytes
- HMAC
    - HMAC(HMAC_key, text) = SHA256({hmac_key_2, SHA256({hmac_key_1, text})})
        - hmac_key_1 = hmac_key ^ ipad
        - hmac_key_2 = hmac_key ^ opad
        - text = {cmd, addr, len, packet_counter, ciphertext}
    - will be using a 16 byte HMAC
        - the upper 16 bytes from the SHA256 output will be used, and the remaining bytes will be ignored
- AES-CTR with 128 bit key
    - first 128 bits of encryption key = FPGA encryption key = HOST decryption key = aes_key_f2h = encryption_key[127:0]
    - later 128 bits of encryption key = FPGA decryption key = HOST encryption key = aes_key_h2f = encryption_key[255:128]
    - nonce = {80{1'b0}, packet_counter}
- needs to enforce:
    - session establishment
    - nonce exchange
    - key derivation
    - host authentication
    - FPGA authentication
    - packet counter tracking 
    - HMAC verification
    - AES-CTR encryption/decryption
    - plaintext release after authentication
    - error lockout 
- communication_controller will mostly remain uncahnged, it will just be some new wiring changes
    - however, with the new architecture, because we aren't stream words as they arrive, the writes will be significantly faster 
    - The security controller presents decrypted packets to communication_controller using the same cmd/addr/len/word_valid/packet_done style interface as serial_packet_rx
    - The security controller accepts plaintext TX packets from communication_controller using the same tx_start/cmd/addr/len/payload_data/payload_valid/payload_advance style interface as serial_packet_tx
- security based CMD will be implemented but those will be eaten before the communication_controller sees them
    - new security layer commands (will be sent via plain-text)
        localparam SEC_CMD_INIT       = 8'hF0;
        localparam SEC_CMD_INIT_RSP   = 8'hF1;
        localparam SEC_CMD_HOST_AUTH  = 8'hF2;
        localparam SEC_CMD_FPGA_AUTH  = 8'hF3;
        localparam SEC_CMD_SEC_NAK    = 8'hF4;
    - new security layer command that will be checked after decrypted:
        localparam SEC_CMD_SESSION_CLOSE    = 8'hF5;
- authentication handshake:
    SEC_CMD_INIT
        Host -> FPGA
        payload = nonce_host

    SEC_CMD_INIT_RSP
        FPGA -> Host
        payload = nonce_fpga

    SEC_CMD_HOST_AUTH
        Host -> FPGA
        payload = HMAC(hmac_key, {HOST_AUTH, nonce_host, nonce_fpga})
        note: HOST_AUTH is some constant that is hardcoded

    FPGA Verify authentication code => authenticated = 1

    SEC_CMD_FPGA_AUTH
        FPGA -> Host
        payload = HMAC(hmac_key, {FPGA_AUTH, nonce_host, nonce_fpga})
        note: FPGA_AUTH is some constant that is hardcoded

    Host Verify authentication code => authenticated = 1
- all normal communication commands will be rejected before authentication, only the security handshake commands will be accepted 
- only payload will be encrypted, I recognize this weakens security, but will be easier to implement, and integrate into our current system
- the security reset that is sent to the communication_controller will only be for the security gate and will not apply to this encryption module        
- option of building different modules for TX and RX, but this takes up more resources (SHA256 core and AES)
    - therefore, we will be using one cerntral security module that shares a singular SHA256 core for the HMAC calculations and a single AES core for encryption
    - we will need a scheduler for the SHA256 core
    - priority will be given in the following:
        1. handshake / authentication
        2. RX HMAC verification
        3. TX HMAC generation
- the security controller will internally contain the serial_packet_rx and serial_packet_tx modules
    - will need to buffer RX ciphertext to wait for HMAC verification
- security keys:
     - entire flow for nonce generation: ROSC_ENTROPY -> SHA256 -> ChaCha CSPRNG
        - note: be careful of synthesis optimization that might damage the ROSC entropy generator
    - overall the system will have 4 keys:
        - root_key (hard-coded key that both FPGA and HOST have)
        - session_key = SHA256({root_key, nonce_host, nonce_fpga})
        - encryption_key = SHA256({session_key, encryption_constant})
            - will be split into FPGA->HOST key and HOST->FPGA key
                - aes_key_f2h = encryption_key[127:0]
                - aes_key_h2f = encryption_key[255:128]
        - hmac_key = SHA256({session_key, hmac_constant})
            - hmac_key will be used to derive the following inside the HMAC:
                - hmac_key_1 = hmac_key ^ ipad
                - hmac_key_2 = hmac_key ^ opad
    - the encryption_constant, hmac constant, ipad, and opad values are open to the public
